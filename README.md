# Напарник — AI-buddy для стажёров Авито

Прототип для кейса Авито «AI-buddy: ИИ-наставник для стажёров» (Hack&Change 2026).

> **AI-buddy ведёт стажёра по стажировке, а прогресс видят все. Каждый вопрос стажёра превращается в знание команды.**

Стажёр спрашивает Напарника о процессах и инструментах отдела и получает ответ из базы знаний **с источником, автором и датой**. Если ответа нет, Напарник подбирает эксперта по авторству страниц или зовёт бадди и готовит вопрос. Отгул и доступы оформляются **через имитации корпоративных сервисов** по цепочке «черновик → подтверждение человеком → квитанция». План адаптации построен по чек-листу стажёра Авито, у каждого шага есть статус и следующий шаг. Права проверяются кодом: каждая роль видит только своё.

Демо построено на синтетическом отделе продуктовой аналитики: 8 человек, 4 роли. Все люди и тексты выдуманы. Тестовые инструкции помечены «тестовая инструкция, не регламент Авито».

## Проверка за 3 минуты (для организаторов и жюри)

Нужен только Docker (Docker Desktop или Docker Engine с Compose v2). Ключи, `.env` и регистрация не нужны: без ключа модели работает заглушка, все сценарии проходят.

```bash
git clone https://github.com/worker4556/naparnik.git && cd naparnik
docker compose up --build -d --wait
```

Первая сборка — 3–5 минут, команда вернёт управление, когда всё готово. Откройте **http://localhost:3000**.

1. **Стажёр.** Вы вошли как Даниил Соколов. Нажмите на кота справа внизу и спросите «Что такое витрина и где лежит витрина объявлений?» — ответ из базы с автором, датой и ссылкой.
2. **Действие с подтверждением.** «Мне нужен отгул в пятницу» → Напарник объяснит порядок и покажет черновик → «Подтвердить» — квитанция `ABS-1042`. Без «Подтвердить» ничего не отправляется; повторите просьбу — Напарник скажет, что такая заявка уже есть.
3. **Вопрос человеку.** «Где взять шаблон презентации для экватора?» — в базе нет, Напарник предлагает бадди и готовит вопрос.
4. **Другая роль.** Кнопка с именем справа вверху → `lead.kovalev`: прогресс стажёров, заявка на согласовании, польза Напарника и поддержка базы.

Полный сценарий по всем ролям — [Порядок проверки](#порядок-проверки-основной-сценарий--5-минут), статус каждого из 36 сценариев — [docs/STATUS.md](docs/STATUS.md).

Остановить: `docker compose down` (данные сохранятся). Начать с чистого листа: `docker compose down -v`.

## Быстрый старт

### Вариант 1. Docker (рекомендуется для проверки)

Нужен Docker Desktop или Docker Engine с Compose v2.

```bash
git clone https://github.com/worker4556/naparnik.git && cd naparnik
cp .env.example .env          # необязательно: ключ модели и токен Telegram; без файла работает заглушка
docker compose up --build -d --wait
```

Откройте **http://localhost:3000** — интерфейс. API — на **http://localhost:8080** (`GET /api/naparnik` — проверка, что сервер жив).

PostgreSQL и Redis запускаются автоматически; данные сохраняются в томе `pgdata`. Обычная остановка — `docker compose down` (без `-v`). Проверка сохранения: создай заявку, выполни `docker compose restart backend` и обнови страницу. Подробнее: [хранение и повторы](docs/PERSISTENCE.md).

**Если что-то не запускается**

| Что видно | Что сделать |
|---|---|
| `port is already allocated` (3000, 8080) | Порт занят другим приложением: остановите его или поменяйте левую часть в `ports` в `docker-compose.yml`, например `"3001:3000"` |
| `unknown flag: --wait` | Старый Compose: запустите без `--wait` и подождите, пока `docker compose ps` покажет `healthy` |
| Страница открылась, но пустая или «Не удалось загрузить данные» | Backend ещё стартует: подождите 10–20 секунд и обновите. Журнал — `docker compose logs backend` |
| Хочется начать сценарий заново | `docker compose down -v && docker compose up --build -d --wait` — стирает заявки, вопросы и привязки Telegram |

### Вариант 2. Без Docker

Нужны **Go 1.27+** и **Node.js 22.12+** для React-интерфейса.

```bash
cp .env.example .env
cd backend && go run ./cmd/server
```

Сервер сам читает `../.env`. Во втором терминале из корня проекта:

```bash
cd frontend
npm ci
npm run dev
```

Откройте **http://localhost:5173**. Vite перенаправляет `/api` на backend `:8080`.

### Модель (внешний API)

| Что | Значение |
|---|---|
| Сервис по умолчанию | **DeepSeek** (OpenAI-совместимый API), модель `deepseek-chat`. Также поддерживается **Anthropic Claude**, модель `claude-opus-5-5` |
| Как подключить ключ | В `.env`: `DEEPSEEK_API_KEY=…` для DeepSeek или `LLM_API_KEY=…` для Claude. Провайдер выбирается по ключу; явно — через `LLM_PROVIDER=deepseek` или `anthropic` |
| Другая модель | `LLM_MODEL=…`; адрес OpenAI-совместимого API — `LLM_BASE_URL=…` |
| Без ключа | Работает **заглушка модели** (`LLM_MODE=stub_ok`): правила вместо LLM, те же инструменты, все сценарии проходят |
| Проверка сбоев | `LLM_MODE=stub_slow` / `stub_timeout` / `stub_error`: интерфейс не блокируется, есть «Повторить» |
| Модель упала | **Упрощённый режим**: тот же вопрос обрабатывают правила через те же инструменты, права и черновики с подтверждением; в чате пометка и кнопки частых действий. Показать: `LLM_MODE=stub_error` → «Нужен отгул» → «в пятницу» → «Подтвердить» |

Пример конфигурации без секретов — [`.env.example`](.env.example). Файл `.env` с ключом в git не попадает (`.gitignore`).

### Уведомления в Telegram (необязательно)

| Что | Значение |
|---|---|
| Токен бота | В `.env`: `TG_BOT_TOKEN=…` от @BotFather (поддерживается и имя `TOKEN_TG`). Без токена бот работает в режиме `log`: сообщения пишутся в журнал сервера, сайт работает как обычно |
| Подключение | Меню учётки (кружок справа вверху) → «Уведомления в Telegram» → «Получить код» → «Открыть @имя_бота» → Start. Код одноразовый, живёт 10 минут (BR-50) |
| Что приходит | Ответ на вопрос, срочный вопрос, сводка вопросов, черновик страницы, заявка ждёт решения, статус заявки, встреча и напоминание включить запись, напоминания за день и за час, утренний план. Только факт и ссылка — без текстов вопросов и ответов (BR-51) |
| Когда | В Docker по умолчанию сразу (`NOTIFY_IGNORE_HOURS=true`, демо). `false` — по правилам: в рабочие часы, обычные вопросы сводкой в 11:00 и 16:00 (BR-20, BR-52) |
| Не засыпает чат | Что накопилось, пока Telegram не был подключён, заново не рассылается: при подключении бот одним сообщением скажет, сколько уведомлений ждёт в Напарнике, и покажет последнее. Несколько несрочных уведомлений к одному моменту приходят одним сообщением «🔔 Новых уведомлений: N»; срочное — всегда отдельно |
| Не забывает людей | Привязка хранится в состоянии (PostgreSQL) и копией в Redis (AOF на томе `redis-data`): после пересоздания состояния бот при старте возвращает привязки. `docker compose down -v` удаляет оба тома — тогда привязку нужно повторить |
| Журнал | Входящие команды бота (без кода привязки) и ошибки опроса пишутся в журнал сервера: `docker compose logs backend \| grep telegram` |

Redis (`REDIS_URL`, в Docker задаётся сам) хранит копию привязок Telegram, одноразовые коды привязки, лимит сообщений модели (`LLM_RATE_PER_MIN`, по умолчанию 20 в минуту), блокировку отправки и кэш поиска по базе и подбора эксперта. Без Redis — память процесса. Счётчики кэша: `GET /api/naparnik`.

| Учётка | Кто | Роль |
|---|---|---|
| `intern.sokolov` | Даниил Соколов, стажёр-аналитик, 1-я неделя | **Стажёр** — основной пользователь |
| `intern.egorova` | Полина Егорова, стажёр (скрыла текст вопросов от бадди) | Стажёр |
| `buddy.belova` | Екатерина Белова, старший аналитик | Бадди (и эксперт) |
| `expert.orlov` | Михаил Орлов, витрины DWH | Эксперт |
| `expert.smirnova` | Ольга Смирнова, A/B-платформа | Эксперт |

| `lead.kovalev` | Андрей Ковалёв, руководитель отдела | Руководитель |
| `director.volkov` | Сергей Волков, директор по аналитике (руководитель руководителей) | Эксперт верхнего уровня: стажёру напрямую не предлагается, вопросы по его темам идут через бадди (SC-35, BR-10a) |

В API учётка передаётся заголовком `X-User: intern.sokolov`.

В React-интерфейсе стартовый экран зависит от роли: стажёр — «Мой день» и «Мой план», бадди — «Мои стажёры» с выбором плана, эксперт — «Входящие» (вопросы ему), руководитель — «Команда» и «Согласование». Руководитель видит прогресс своих стажёров, просрочки, количество открытых вопросов и заявки. Тексты личных вопросов в обзор не входят; отмечать шаги может стажёр или его бадди.

Проверка ролей: откройте план Даниила, переключитесь на Андрея Ковалёва — появится обзор двух стажёров без личных задач и чекбоксов. У Екатерины Беловой можно выбрать план Даниила или Полины; неутверждённый план Полины показан как «План готовится». При смене учётки предыдущие данные и чат очищаются, ответы старых запросов игнорируются.

**Нет доступа к системе (SC-33).** Под учёткой `intern.sokolov` спросите: «Хочу сам посмотреть данные в витринах DWH, как туда попасть?» Напарник объяснит: доступ только на чтение положен со второй недели, связан с шагом плана и согласуется Андреем Ковалёвым. Объяснение не отправляет заявку. Выберите «Сделай за меня» → проверьте черновик → «Подтвердить»: квитанция появится в чате и заявках. Или выберите «Оформлю сам» и воспользуйтесь формой «Заявки» → «Оформить самому» → «Доступ». Раннюю заявку согласует руководитель; выданный доступ и заявка на согласовании отображаются без предложения повторной заявки. Закрытые страницы и системы с ПДн для объяснения не используются. API правил: `GET /api/services/access/rules?system=sys-dwh-marts-ro`, заголовок `X-User: intern.sokolov`.

## Порядок проверки (основной сценарий, ≈ 5 минут)

Демо-дата — **среда, 11 ноября 2026**, 3-й день стажировки Даниила. Учётка `intern.sokolov`.

Сценарий ниже проверяется в интерфейсе на **http://localhost:3000**. Кнопки названы как в интерфейсе; фразы в кавычках вроде «да, подготовь вопрос» или «Сделай за меня» — это ответы, которые ты пишешь в чат сам.

1. **Утро стажёра (SC-01, SC-18).** На «Мой день» — 3 шага, просроченный «Доступ к Redash» первым, событие дня (1:1 в 15:00), прогресс по этапам плана.
1а. **Знакомство с командой (SC-02).** У шага «Познакомься с командой» нажать «Карта команды»: бадди первым, у каждого — зона ответственности, часы работы и его страницы в базе (открываются в «Базе знаний»). «Написать» → черновик знакомства → «Скопировать»; отправляет стажёр сам, Напарник ничего не пишет коллегам (BR-62). Директору черновика нет — вопросы через бадди (BR-10a).
2. **Доступ по шагу плана (SC-27).** У шага Redash нажать «Помоги» → в поле чата появится «Помоги с шагом: …», отправь его → Напарник объясняет порядок по тестовой инструкции → черновик заявки → «Подтвердить» → квитанция `ACC-2002`. Заявка видна в разделе «Заявки».
3. **Ответ из базы (SC-03).** Маскот (справа внизу; его можно перетащить к любому краю, правый клик — «Свернуть», «Скрыть на час», «Настройки») → «Что такое витрина и где лежит витрина объявлений?» → ответ со ссылкой на страницу Михаила Орлова, дату и автора; кнопки «Помогло / Не помогло / Устарело».
4. **Вопрос человеку (SC-04, SC-07).** «Где взять шаблон презентации для экватора?» → в базе нет → Напарник предлагает бадди Екатерину → «да, подготовь вопрос» → черновик → «Подтвердить». Без подтверждения ничего не уходит (SC-05: «Отмена»).
   В карточке вопроса нажми «Изменить вопрос»: поправь текст, при необходимости включи «Срочно — без ответа не могу продолжить работу», затем «Сохранить изменения». Вопрос пока не отправлен — проверь его и отдельно нажми «Подтвердить». Перезагрузка сохраняет правки: открой чат, ожидающий черновик восстановится. «Отмена» сохраняется на сервере, после неё вопрос уже нельзя отправить, в том числе из другой вкладки. Если другая вкладка изменила черновик, старое подтверждение отклоняется и показывается актуальный текст.
5. **Отгул (SC-14).** «Мне нужен отгул в пятницу» → порядок, проверка даты, выбор «сам или за тебя» → «Сделай за меня» → черновик → «Подтвердить» → квитанция `ABS-1042`. Без ключа модели (заглушка) Напарник сразу показывает черновик, не спрашивая «сам или за тебя». Если отгул на пятницу уже оформлен (например, в «Проверке за 3 минуты»), Напарник ответит «Такая заявка уже есть: ABS-1042» — это защита от повторной заявки; повторите шаг с другой датой.
5а. **Ответ эксперта → знание команды (SC-04, SC-12).** Даниилом: «Почему конверсия в дашборде отличается от выгрузки из DWH?» → «да, подготовь вопрос» → «Подтвердить» (вопрос уходит Михаилу Орлову). Переключиться на `expert.orlov` → «Входящие»: вопрос уже открыт карточкой с полем «Твой ответ» → ответить → в блоке «Проверь, я занёс твой ответ в базу» нажать «Ок, опубликовать». Переключиться на `intern.egorova` и спросить «Почему конверсия в дашборде не совпадает с DWH?» → ответ сразу из новой страницы Михаила.
5б. **«Сделай сам» и согласование (BR-42, SC-14, SC-27).** «Заявки» → «Оформить самому» → отгул на 20 ноября: форма сразу предупреждает о сроке, встрече и дедлайне шага → «Отправить в сервис». Вкладка «Доступ» → Redash → «Отправить в сервис». Заявки появляются в списке «На согласовании» с пометкой «оформлена сам». Переключиться на `lead.kovalev` → «Согласование»: «Ждут твоего решения: N» (все заявки этого прогона) → «Выдать» доступ, отгул «Отклонить» с причиной из сервиса и комментарием. Вернуться к `intern.sokolov`: статусы и уведомления обновились, в карточке доступа — история и кнопка «Отметить шаг выполненным». Если открыть Даниила и Андрея в двух вкладках, решение руководителя появится у стажёра само, за пару секунд, без обновления страницы (живые обновления, `GET /api/stream`).
6. **Права и границы (SC-16, SC-17, SC-28).** «Покажи данные витрины с персональными данными клиентов» → отказ. «Меня возьмут в штат?» и сообщение с паспортом → отказ **до обращения к модели**.
   Проверка оценок: `POST /api/feedback` с `X-User: intern.sokolov` и `{"page_id":"kb-R1","value":"stale"}` возвращает 404 без события и уведомления; для `kb-03` оценка сохраняется. После встречи с записью выжимка и таймкоды доступны в общей статье, а «Открыть запись встречи» — только участникам в разделе «Вопросы».
7. **Другие роли (SC-13, SC-29).** Переключиться на `buddy.belova`: виден план Даниила и маршрут его вопросов. У `intern.egorova` текст вопросов от бадди скрыт. Переключиться на `lead.kovalev`: виден план стажёра и квитанции, тексты вопросов — нет.
8. **Встреча вместо текста (SC-10, SC-11).** Даниилом: «Как выбрать длительность A/B-теста для низкого трафика?» → вопрос уходит Ольге Смирновой. Под `expert.smirnova` в карточке вопроса «Проще голосом — назначить встречу» → 3 слота в рабочие часы обоих (12.11 11:00 и 14:00, 13.11 10:00) → выбрать слот: Даниилу приходит приглашение, встреча — в его «Ближайшем». После встречи «Встреча записана — собрать ответ» → черновик страницы с таймкодами без посторонних тем → «Ок, опубликовать». Ссылка «Открыть запись встречи» доступна только участникам в карточке вопроса; в общей статье её нет. Вариант «Записи не было» → предложение ответить текстом → «Нет, оставить открытым» → вопрос у владельца базы. Запись и транскрипт — заглушка ВКС ([meetings.json](docs/04-mock-data/meetings.json)).
9. **«Не ко мне» и переадресация (SC-08, SC-09).** Адресат вопроса → «Не ко мне» → выбрать коллегу или «пусть Напарник подберёт». Под `buddy.belova` в «Вопросах стажёров» → «Переадресовать». В карточке виден маршрут («Михаил → Наталья → Ольга»), стажёр и адресаты получают уведомления.
10. **Топ-руководитель (SC-35, BR-10a).** Даниилом: «Планируют ли менять North Star раздела?» → вопрос уходит бадди, имя директора Даниил не видит. У Екатерины в карточке подсказка «по теме больше всех писал Сергей Волков, директор по аналитике» и кнопка «Переадресовать».
11. **Гриф «конфиденциально» (SC-36, BR-49).** Даниилом: «Что с запусками в разделе объявлений в первом квартале?» → Напарник называет страницу «План запусков…» с пометкой «конфиденциально» и не пересказывает её: текст страницы во внешнюю модель не уходил. В «Базе знаний» страница открывается целиком.

### Практика перед первой задачей (SC-30…SC-32)

 На «Мой день» и «Мой план» появился блок «Практика перед задачей». Черновик готовится автоматически по `practice.json` при открытии экрана стажёра или бадди; исторические примеры попыток из JSON не загружаются как результаты пользователя.

1. Переключитесь на Екатерину Белову: в блоке практики Даниила можно поправить текст и нажать «Одобрить задание».
2. Вернитесь к Даниилу: «Начать практику» → общие термины → термины и правила команды → учебное задание. Источники открываются целиком с автором и датой.
3. Введите учебный SQL и описание результата (имя таблицы, название графика и папка). «Проверить попытку» даст обратную связь по каждому критерию со ссылками. Не больше 3 попыток; после третьей неудачи можно подготовить вопрос бадди и отдельно подтвердить отправку.
4. У Екатерины видны лучшая попытка, число попыток и темы ошибок; остальные ответы и диалог скрыты. У Даниила успешная попытка открывает чек-лист реальной задачи. Реальная задача не отмечается выполненной автоматически.
5. Любой этап можно пропустить. Если бадди не одобрил задание за один рабочий день, стажёр продолжает без задания, а черновик остаётся у бадди.

На демо-дате 11 ноября практика доступна заранее; для предложения в день срока шага `s-13` установите `DEMO_TODAY=2026-11-30` в `.env` и пересоздайте backend (`docker compose up -d --force-recreate backend`). В текущем трекере срок этого шага — 30 ноября. Для отдельной проверки дедлайна API-тесты сдвигают дату с пятницы на понедельник. В заглушке проверяется текст учебного SQL по правилам из шаблона; SQL здесь не исполняется. С ключом модели генерация и проверка выполняются выбранным LLM-провайдером.

Что реализовано, а что нет, по каждому сценарию SC-01…SC-36 — в [docs/STATUS.md](docs/STATUS.md).

### Подключение настоящих сервисов, аналитика, флаги

Инструменты агента работают с сервисами через интерфейсы ([spec/09](docs/spec/09-adapters.md)); по умолчанию за ними имитации на мок-данных.

| Переменная | Что |
|---|---|
| `ABSENCE_SERVICE_URL`, `ABSENCE_SERVICE_TOKEN` | Настоящий сервис отсутствий по REST (`GET /catalog`, `POST /requests` с `Idempotency-Key`, `GET /requests/{id}`) вместо имитации |
| `ABSENCE_SYNC_SEC` | Как часто спрашивать сервис отсутствий о решениях согласующего (по умолчанию 60 с). Решение применяется так же, как в интерфейсе: история заявки, уведомление стажёру, событие в журнале |
| `EVENTS_URL`, `EVENTS_TOKEN` / `EVENTS_FILE` | Выгрузка журнала событий пачками в коллектор (Clickstream, REST-прокси Kafka) или в JSONL-файл |
| `FEATURE_FLAGS`, `FLAGS_FILE` | Флаги `practice`, `glossary`, `meetings`, `telegram`, `watchers`; файл перечитывается на лету, можно по ролям |

Состояние флагов и выгрузки — `GET /api/naparnik`.

## Архитектура и стек

```
Браузер ──► React (Vite / nginx) ──HTTP──► backend (Go): API + агент + имитации сервисов ──► LLM
                                              │      │      │
                                     PostgreSQL   Redis   Telegram Bot API (уведомления)
                                              │
                                              └── тестовые данные docs/04-mock-data
```

| Часть | Технологии | Версии |
|---|---|---|
| Backend и агент | Go, стандартный `net/http` | Go **1.27.3** |
| LLM | `anthropic-sdk-go`, `openai-go` (DeepSeek и OpenAI-совместимые) | **v2.8.0**, **v3.98.0** |
| Frontend | React + TypeScript + MUI, Vite; проверка ответов сервера — Zod; живые обновления — SSE; структура Feature-Sliced в `frontend/src/` | см. `frontend/package.json` |
| Хранение | PostgreSQL (состояние, журнал событий), Redis (коды, лимиты, кэш поиска) | `postgres:16-alpine`, `redis:7-alpine`, `go-redis` **v9.7.3** |
| Запуск | Docker (`golang:1.27-alpine` для backend, `node:22-alpine` → `nginx:alpine` для frontend), Docker Compose | — |
| CI | GitHub Actions: vet, тесты, порог покрытия, сборка образа | — |

Ключевые решения — в SDD-спецификации агента: [docs/spec](docs/spec/00-overview.md).

- **Модель выбирает, код решает.** Модель выбирает инструмент, а права, проверки и выполнение — в коде (BR-40).
- **Лестница доверия.** Всё, что создаёт заявку или пишет людям, сначала становится черновиком и выполняется только по кнопке человека (BR-11, BR-43).
- **До модели.** Персональные данные и вопросы об оценке и штате отсекаются кодом и не уходят во внешний LLM (BR-60, 61, 72).
- **Два пути к заявке (BR-42).** «Сделаю за тебя» — черновик Напарника; «сделай сам» — форма имитации сервиса. Обе заявки попадают в один сервис и согласуются руководителем с кодом причины.
- **Адаптеры.** Сервисы отсутствий и доступов, база знаний, трекер, календарь и ВКС — имитации на данных `docs/04-mock-data`. Замена на реальные системы Авито меняет адаптер, а не агента ([11-INTEGRATION](docs/03-requirements/11-INTEGRATION.md)).
- **Журнал событий (BR-73).** Каждое действие пишется в той же транзакции, что и само действие; из журнала строятся уведомления и метрики пользы.

## Ограничения прототипа

- В Docker состояние сохраняется в PostgreSQL. Без `DATABASE_URL` режим остаётся временным, в памяти. История разговора модели после перезапуска сбрасывается; заявки, вопросы, страницы и прогресс в PostgreSQL сохраняются. См. [PERSISTENCE](docs/PERSISTENCE.md).
- ВКС — заглушка: итог встречи отмечает организатор кнопкой, расшифровка — готовая фикстура.
- Все сценарии SC-01…SC-36 из [06-TEST-PERSONAS](docs/03-requirements/06-TEST-PERSONAS.md) реализованы. Не заявлены как готовые и вынесены в «следующий шаг»: возврат плана бадди с комментарием (SCR-L2), вебхук сервиса отсутствий. Подробно — в [docs/STATUS.md](docs/STATUS.md).
